## Per-reviewer findings

### Security Reviewer (security, privacy) — verdict: request changes

The three hardenings named in the brief are **present in the tree**, and two are
genuinely effective: pagination origin validation (`safe_url.safe_next` is called by
all five pollers; a cross-origin absolute `next` URL is dropped to `None`) and
allowlisted env base URLs (`poll_nvidia.py:41-55`, `poll_gemini.py:40-56` reject
evil/suffixed/userinfo hosts). Atomic writes are present (`atomic_io.py:63-78`
mkstemp → fsync → `os.replace`), and there is no unsafe deserialization anywhere
(`safe_load`/`safe_dump` only; no `pickle`, `eval`, `exec`, or `subprocess` in the
tree).

What remains is a set of **fail-open fallbacks** and open trust-boundary crossings.

- **blocker** — `safe_url.py:21-29` — `same_origin()` returns `True` for anything
  `origin_of()` cannot parse (scheme-relative `//evil/x`, scheme-less, whitespace,
  `javascript:`, non-strings). Verified: `safe_next('//evil.example.com/collect', BASE)`
  returns the URL, not `None`. The guard degrades to "allow" instead of "deny".
  The inline `safe_next` shims duplicated in each poller are worse — a bare pass-through
  on import failure. Fix: deny on uncertainty; delete the five duplicated shims in
  favour of the `sys.path`-guaranteed import already done correctly in
  `poll_template.py:13`; add a regression test.
- **major** — `poll_base.py:65-71` — `except Exception: return nxt` fail-open in the
  shared helper. Any exception from `safe_url` returns the raw server-supplied URL,
  which is then fetched with the provider's `Authorization` header attached.
- **major** — `select-models.py:941-945` — Gemini key placed in the query string
  (`?key={api_key}`) instead of the `x-goog-api-key` header that `poll_gemini.py:522`
  correctly uses; and the remotely-sourced `model_id` is concatenated into the URL path
  with no percent-encoding and no character allowlist. (Note: `README.md:102` claims
  both `?key=` **and** the header are sent — the header is not in the code.)
- **major** — `poll_nvidia.py:48` / `poll_gemini.py:47` — `_host in ("", "…official…")`
  accepts an empty authority. Verified at runtime:
  `NVIDIA_BASE_URL='file:///etc/passwd'` → `'file:///etc/passwd/models'`, which
  `urlopen` will fetch. The scheme is never checked, only the netloc.
- **major** — `hermes-setup.ps1:198-203` — remote installer executed with no hash pin
  (`$ScriptVersion = '3'` is not a content hash). The selector fetch at
  `hermes-setup.ps1:142-156` only greps for `def choose_default`.
- **major** — `Set-ModelSelectorTask.ps1:57-71` + `Run-ModelSelectorTask.ps1:3` — the
  task's execution target is a user-writable, predictable file in the repo tree, run
  with `-ExecutionPolicy Bypass`. Anything able to write into the checkout replaces
  what runs at 04:00. Compounded by the predictable temp path in
  `hermes-setup.ps1:142`.
- **major** — `NightlyRestartTask.ps1:199-215` — `-ExtraTasks` paths invoked via
  scriptblock with no path validation; their output is written to the Application
  event log.
- **minor** (5) — non-atomic poller output writes + `--out` path traversal; non-atomic
  `config.yaml` backup at `select-models.py:1045-1049`; `importlib.exec_module` of a
  sibling `.py` (`select-models.py:452-464`); nits on return-value fidelity, homoglyph
  matching, cleartext `http://` pagination, `-ExecutionPolicy Bypass`, inline
  `__import__("json")`.

Full report: `review-report_SECURITY.md`.

### Concurrency Reviewer (concurrency, resilience) — verdict: request changes

The thread-parallel core is healthy where it matters: per-provider results are merged
on the main thread, cache access is guarded by a `threading.Lock`, and prints are
guarded by a `print_lock`. The uncontrolled writes are at the **cross-process level**.

- **blocker** — `hermes-model-selector.py:210-214` (`save_history`), plus its callers
  at `:919`/`:950`, and `select-models.py:1498` (`save_promotion_history`) —
  `promotion_history.json` is written by **both** selector scripts, and nothing locks
  it. Two concurrent runs (nightly task + manual run) interleave `load → update → write`;
  the later write silently clobbers the other run's fold. Since the promotion gate reads
  `consecutive_clean_passes` from this file, one process can erase the other's evidence
  and promote the wrong model. Fix: wrap `load → update → save` in `atomic_io.file_lock`
  in **both** scripts.
- **major** — `select-models.py:1493-1498` — the `atomic_io.file_lock` block that wraps
  the probe phase **closes before** the promotion-history update, so the parallel path's
  only write to that file is unprotected.
- **major** — `hermes-model-selector.py:186-192` — `save_fallback_cache()` writes
  `fallback_model_cache.json` with no lock and no TTL; its snapshot assumption breaks
  under partial/old writes.
- **minor** — `select-models.py:1402-1435` — the targeted-retest branch writes the cache
  outside the in-memory `cache_lock` (created at `:1442`, after that branch).
- **minor** — `select-models.py:513-540` / `hermes-model-selector.py:322` — lazy
  check-then-act global init (`_OR_CONTEXT_MAP`, `_OR_MAP`) is not thread-safe.
- **nit** — `atomic_io.py:21-82` — primitives are sound (`msvcrt`/`fcntl` advisory lock
  with deadline; mkstemp+fsync+os.replace). `.lock` files are never removed; harmless.

No concurrency tests exist; the cross-process race is established by code inspection,
not stress-tested.

### Architecture Reviewer (architecture, compatibility) — verdict: request changes

The poller/registry layer is good architecture: bounded, uniform, testable, no config
writes. The selectors have not converged. The dominant issue traces to one unresolved
decision in `selector-intention.md`: **ownership of `model.default` +
`fallback_providers` is not defined.**

- **F1 major** — `select-models.py:1041-1115` (invoked `:1577-1578`) and
  `hermes-model-selector.py:728-810` write the **same keys** with **incompatible
  semantics** (merge vs replace). Whichever script runs last wipes the other's fallback
  entries, which can drop a working chain or bypass the Nous promotion gate.
- **F2 major** — `select-models.py:458-485` lazy-loads `hermes-model-selector.py`
  internals (`HARDCODED_DATES`/`_OR_MAP`), and `:1170-1178` hard-codes
  `import poll_nvidia` + `_is_chat_like` instead of using the registry's polymorphic
  `fetch_fn`. Both break the registry/poller contract the docs specify.
- **F3 major** — `select-models.py:819-835` executes `import hermes_ollama_selector`,
  but the file is `hermes-ollama-selector.py` (hyphens) — no such module exists →
  `ModuleNotFoundError` → the registered provider always errors. Combined with
  `default_enabled: False`, local Ollama is effectively unusable in `select-models.py`.
  (Same import at `:998` and `:1022`.)
- **F4 major** — NVIDIA lacks its `slug` key in the registry (`providers.py:37-52`) and
  is wired as a hard-coded branch (F2), so the registry contract is not the delegation
  mechanism for the two hard-coded cases.
- **F5 major** — `ollama-cloud` is `default_enabled: True` with `probe: False`
  (`providers.py:69-83`); `_process_provider` (`:1150-1167`) records these as
  `clean_pass: True` into `promotion_history.json`, inflating `consecutive_clean_passes`
  every night.
- **F6 major** — the Nous registry entry (`providers.py:114-128`) has `probe: False` and
  says auth is "handled by hermes-model-selector", but `select-models.py:1187-1216`
  probes Nous against `inference-api.nousresearch.com` with no token, so it can never
  pass Nous models. The two chains are mutually subtractive (F1).
- **F7 major** — config-write conventions are split three ways: `yaml.safe_dump`
  (select-models), ruamel `atomic_roundtrip_yaml_save` (hermes-model-selector), and a
  `yaml.safe_dump` fallback when ruamel is missing (`hermes-ollama-selector.py:386-400`).
  No single authority on config format.
- **F8 major** — the `model_ranking` matrix only affects which models are probed under
  `--top N` and display order; the gate re-sorts by release date, so weights are nearly
  decorative for the promotion decision.
- **F9 major** — the "clean pass" definition differs between the two implementations
  (`select-models.py:1217-1222` vs `hermes-model-selector.py:511-512`), so the same run
  can produce different streaks in the two history stores.
- **F10 major** — fallback chain entries are `{"provider", "model"}` pairs with no
  endpoint/base_url (except `custom`), so re-running with a different provider set
  silently changes the meaning of existing entries.
- **F11 major** — release-date resolution is duplicated (`select-models.py:418-510` vs
  `hermes-model-selector.py:384-397`) and can assign different dates to the same model;
  `hermes-model-selector.py:378` hardcodes dates and `:611-612` hardcodes a dead usage
  dict. Release date is the gate's primary sort key.
- **F12-F16 minor** — three probe implementations with three "clean pass" rules; the
  per-provider probe budget is undocumented; output-convention drift (`HERMES_HOME/cache`
  vs `out/<provider>.json`); dead surface (`providers.ALWAYS_TRY` unused at `:181`);
  inconsistent CLI parsing (argparse vs hand-rolled `sys.argv` at
  `hermes-model-selector.py:823-862`).

**Before approving, the architecture reviewer requires:** (1) a single owner for
`model.default` + `fallback_providers` with one config-writer contract; (2) removal of
the hard-coded `poll_nvidia`/`hermes-model-selector` dependencies and a working
`ollama-local` path; (3) a decision on whether listing-only providers may vote in the
gate; (4) one YAML writer and one release-date path.

## Overall verdict: request changes

Top 3 blockers:

1. **Cross-process write race on shared promotion history.** `promotion_history.json`
   (and `fallback_model_cache.json`) are written by both selector scripts with no file
   lock, and `select-models.py`'s parallel-path save sits outside its own `file_lock`
   section. Two concurrent runs silently clobber each other's streak, which can promote
   the wrong model. *(Concurrency blocker + Architecture F1)*
2. **`safe_url.same_origin()` fails open.** The single control the whole pagination
   design rests on returns `True` for any input it cannot parse — verified at
   `safe_url.py:24-25` — and `poll_base.py:71` returns the raw unvalidated URL on any
   exception. The headline mitigation is currently a hint, not a guard. *(Security B1)*
3. **Two-writer conflict plus a broken import.** `select-models.py` imports
   `hermes_ollama_selector`, which does not exist (the file is
   `hermes-ollama-selector.py`), so the `ollama-local` provider always errors; and its
   merge semantics fight `hermes-model-selector.py`'s replace semantics over the same
   config keys. *(Architecture F1/F3 + X1/X4)*

Nothing here is a drive-by remote exploit on its own — each requires an upstream
compromise, a local writer, or a network-position attacker. But the documented
hardening is not yet the load-bearing control it is presented as, and the ownership
question behind X1 is the thing that will keep producing findings until it is decided.

**Suggested order of work:** X1/X2 (one config-writer owner + lock the shared files) →
Security B1/M1 (invert the origin guard, fail closed) → X3 (don't let unverified models
vote in the gate) → X4 (fix the `hermes_ollama_selector` import, drop the hard-coded
sibling couplings) → the security majors M2–M6 (Gemini key as a header, allowlist
`file://`, pin the installer, harden the scheduled-task trust root) → documentation
accuracy (X7).
